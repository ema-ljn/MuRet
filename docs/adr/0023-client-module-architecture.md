# 0023. The client in modules: three roots, layers and one handler per packet

**Status** · Proposed in AR0.1 (2026-11-21), on the plan Emanuel chose that day (by epics, interleaved with the port).
It becomes accepted when the refactor closes (AR7).

## Context

The client grew wave by wave in a few folders, and everything builds into one `ClientLib`. Measured on `main` `bb56680`
([spec](../superpowers/specs/2026-11-20-client-architecture-design.md#what-we-measured)):

- `Scenes/` is 61% of the client (164k of 269k lines, 687 files): actors, monsters, effects, inventory, chat, guilds,
  events and the HUD.
- `WorldState` and `WorldRuntime` are god objects: each is included by about 195 files, and `Runtime()` is called
  1,273 times.
- Adding a packet touches six files in three layers (`ServerSession` → `WorldEvent` → `SessionEventApplier` → …).
- With the target map, 365 includes in 83 module pairs go up a layer, 11 of them from the engine, and 80 pairs of game
  modules of the same layer include each other.

TrinityCore and MaNGOS show where this ends: their `game` is one library whose folders form a single cycle (49 of 51 in
TrinityCore), and the only clean boundary is between libraries, because the linker enforces it. OpenMU shows the other
side: small handlers per packet and one folder per feature.

## Decision

- **Three include roots, one target per module:** `engine/` (14 modules, layers 0 to 5), `game/` (44 since
  `game/Music`, 2026-11-25; layers 6 to 11) and `app/` (12). A module uses only lower layers and, inside its layer, the
  modules its `may_use` names in `Client/modules.tsv`. No cycles. The table is in
  [CODING_RULES §5](../CODING_RULES.md#5-capas-separadas).
- **Every file has a module** in `Client/docs/research/coverage/module-map.tsv`, and `check_layers.py` checks the
  includes in CI against a baseline that only shrinks.
- **Protocol:** offsets in the type (`Field<T, Offset, Endian>`), a `constexpr` opcode table with one row per `case` of
  the original dispatcher and `Unported{va}` rows for what is still missing, and one handler per packet in its module's
  `In/` (AR2).
- **State per module:** `globals.tsv` maps each global of the original to its MuRet field and module, and the
  `GameContext` replaces access through `WorldRuntime` (AR3). Contiguous data of the original is not split.
- **Scenes are ordered frame scripts** that call the modules in the original's order (AR5). Fan-outs are ordered lists
  assembled in `app/`, never registered at runtime.
- **From the references:** from OpenMU, small handlers per packet, one action per player intent and features as
  folders; from TrinityCore and MaNGOS, the opcode table, packets typed per feature, the format reader below and the
  tables above, one folder per instance or map with its ids header, and target boundaries; from MuMain, folders by layer
  and domain. Not taken: plugins and runtime registration, unordered hooks, singletons, `game` as one target, MuMain's
  one-frame-behind drawing (ADR 0003 there), and behavior as data.

## Consequences

- A boundary is checked by a tool, not by memory: `check_layers.py` in the `includes` job (AR0.1) and, once the roots
  exist, the compiler (AR1.2).
- No refactor PR changes behavior: the per-frame behavior golden (AR0.3) and every current test stay identical. Moves
  are generated by `move.py` and checked by `check_pure_move.py` (AR0.2), and citations keep their wave through
  `.git-blame-ignore-revs`.
- A new packet touches its layout, its handler and one table row (AR2).
- Cost: 33 large PRs over eight epics, a moving map that port PRs must keep up to date, and a foundation branch
  (`refactor/client`) that has to take `main` in regularly.
