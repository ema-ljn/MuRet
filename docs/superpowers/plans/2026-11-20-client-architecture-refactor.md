# Client architecture refactor: plan by epics

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** split the client into an engine, a protocol, a kernel and small game modules, with dependencies going one way
and without the same logic written several times, without changing a single byte of behavior and without losing track of
what is still unported.

**Architecture:** three include roots with their targets (`engine/`, `game/`, `app/`), an opcode table with one handler
per packet, the original's state split per module and the scenes as ordered frame scripts. We get there by epics (AR0 to
AR7): first the safety net and tracking, then the engine, the protocol and the state, and finally `Scenes/` split into
modules, one group per milestone.

**Tech Stack:** C++20, CMake 3.25 (`FILE_SET HEADERS`, `VERIFY_INTERFACE_HEADER_SETS`), GoogleTest, Python 3 with the
standard library and `unittest` for the tools, GitHub Actions.

**Spec:** [`docs/superpowers/specs/2026-11-20-client-architecture-design.md`](../specs/2026-11-20-client-architecture-design.md)

**Annex:** [`2026-11-20-client-architecture-refactor/`](2026-11-20-client-architecture-refactor/): the map of the 1,418
files of `Client/src` to their target module (`module-map.tsv`, the seed), the 26 candidate modules of `Scenes/` with
their dependencies and the state they touch, the 100 pairs that include each other and the 132 interfaces and parameter
bags.

## Global Constraints

- No refactor PR changes behavior: the behavior golden (AR0.3) and every current test and golden stay identical on Linux
  and Windows, Debug and `math-release`. A difference is a refactor bug, not a golden to regenerate.
- A move (a PR that only moves files) is generated by `Client/tools/architecture/move.py` from `module-map.tsv` and
  verified by `check_pure_move.py`. It never mixes in logic: logic goes in the design PR that follows it.
- Commits, PR titles and branches use Angular notation (Emanuel, 2026-11-21; `AGENTS.md`), with the milestone as the
  scope: a move is `refactor(AR1.2): move the engine to Client/src/engine` on branch `refactor/ar1.2-engine-move`, a
  comments PR is `docs(AR1.2): trim and translate comments`, a design PR is `refactor(AR1.1): …`, and a tool is
  `feat(AR0.2): …` or `ci(AR0.1): …`. Never `CLn` in the scope, so `git blame` does not assign them a wave.
- The order of the original's calls and `rand()` calls does not change; every fan-out between modules is an ordered list.
- A folder that only changes root keeps its includes (`"Core/Expected.h"` stays the same: the target's include root
  changes); a file that changes folder (`Scenes/X.h` → `Guild/X.h`) does not, and `move.py` rewrites those includes and
  nothing else.
- New scripts use only the standard library, run with `python3 -I`, and their tests use `unittest`.
- At most 3 agents in parallel (Emanuel, 2026-11-19), counting the port's and the reviews.
- Each step uses the skill that fits it ("Skills for each step"), and the three new repo skills are born together with
  what they describe.
- Everything in English (Emanuel, 2026-11-21): branches, commits, PR titles and descriptions, code comments, docs, file
  and tool names. A comment goes in only if it is strictly necessary, short and
  on one line (CODING_RULES §9): the citation to the original (`// 0x4d3200`), which tracking reads, and a why the code
  cannot say. Existing Spanish docs are translated by the
  [docs translation plan](2026-11-21-docs-to-english.md).
- Clean Code is the refactor's guide (Emanuel, 2026-11-21): every design PR is written and reviewed with the
  `clean-code` skill, every step follows the `refactoring` loop, and module boundaries follow `clean-architecture`. They
  rank below fidelity and `CODING_RULES.md`: a style rule does not change the order of calls, of `rand()` calls or the
  rounding of a `float`. Moves clean nothing up.
- Large PRs per milestone (Emanuel, 2026-11-11), with the move, the comments and the design in separate PRs (the move
  and the comments are reviewed by script; the design, by eye).
- Names (Emanuel, 2026-11-22 and 2026-11-23): no `MuRet` prefix. Targets and binaries take the module's word
  (`Core.dll`, `Game.dll`, `main.exe`); CMake options and functions, macros and environment variables use `MU_`/`mu_`,
  and `MU_CLIENT_` for the client's own. The `MURET_` and `MuRet` names below predate that; each epic's detailed plan
  uses the new ones.

## Review Focus

- A line moved by the move that also changed (an include that dragged a definition along, a `using` that got lost):
  `check_pure_move.py` must flag it even if the file compiles.
- A cut in `entradas/cortes-vivos.tsv` whose line was moved **and** later edited: the anchor must still find it if the
  addresses and the name did not change, and say "unresolved" (not invent a file) if it disappeared.
- A move commit without the `AR` scope in its title, or a squash not listed in `.git-blame-ignore-revs`: the matrix
  generator must warn instead of attributing the citations to the previous commit's wave.
- A behavior golden scene that depends on the real clock or on the order of an `unordered_map`: the harness must give the
  same hash twice in a row on the same machine and on both CI machines.
- A new include that crosses layers in a port PR while the refactor is half done: `check_layers.py` rejects it even if
  the base already has old violations (baseline ones do not count; new ones do).

the comments of the files it moved, and of their tests, to the rule in CODING_RULES §9: what repeats the code is

touched.

## The two lanes: the refactor and the port

The port (gaps, traces, cuts, VM) does not stop. The rules:

1. **New code goes to its target module.** `module-map.tsv` gives each file's target; a new file in a port PR adds its
   row in the same PR. If the module does not exist yet, the file goes where it would go today but already with the new
   anatomy (one handler per packet, the state it touches in the signature), and its group's move carries it.
2. **A module being moved receives no port work that day.** The move is a script: if `main` changed, it is rerun on the
   new `main` instead of resolving conflicts by hand. A module's design and port work on the same module do not run at
   the same time.
3. **Agents:** the refactor uses at most 2 of the 3 (one writes and one reviews) and leaves at least 1 to the port.
4. **What is still unported stays visible:** cuts keep their text; the reference adds the `module` column and
   `consultar.py module <Module>`; from AR2 on, every unported dispatcher `case` is an `Unported{va}` row in the opcode
   table. Before each epic a snapshot of `metricas.tsv` is taken, and when it ends they are compared: the port numbers
   must be the same (except for what the port closed in between).

### AR1.3 (design): the command line, by each system's conventions

Emanuel, 2026-11-21: on Linux nobody writes `connect /u<host> /p<port>`. There the client's arguments follow the Unix
convention (`--name`), Windows uses its most common one (`/name`), and every option is in English.

- **Today** (`App/CommandLine.cpp`, CL3.4) one parser serves both systems. MuRet's own options look like GNU ones
  (`--frames N`) but have no `--opt=value`, no `--`, no `-h`/`--help` and no `--version`. The server only comes in the
  launcher form, `connect /u<host> /p<port>` (Q-C36, D-C10), on Linux too: `Client/README.md` documents it that way.
  Any argument that starts with `/u` or `/p` is read as the launcher form, which on Linux is also how an absolute path
  starts (`/usr/…`). The usage line and the messages are in Spanish.
- **Linux (any POSIX build): GNU syntax only.**
  - The server is `--host HOST --port PORT`, the names of `[Server] Host` and `Port` in `muret-client.ini`. One without
    the other is an error, as today.
  - Every option with a value takes `--opt value` and `--opt=value`. `--` ends the options.
  - Arguments that are not options are ignored, the launcher form included: `connect /u<host> /p<port>` sets no server
    on Linux and is not an error (Emanuel, 2026-11-21: they are ignored because the convention is `--name`). So is
    everything after `--`.
  - `-h`/`--help` prints the usage with every option to stdout and exits 0. `--version` prints `MURET_VERSION` and
    exits 0.
  - A usage error (an unknown `--option` or `-x`, a missing or bad value, a repeat) prints one line that names it and
    then the same usage with every option, as Linux programs do (Emanuel, 2026-11-21), to stderr, with exit code 2. A
    startup error (the data folder, the keys) keeps exit code 1 and prints no usage.
- **Windows: its own style, plus the launcher form** (Emanuel, 2026-11-21: Windows uses its most common convention).
  - MuRet's options as `/name value` and `/name:value` (`/host 10.0.0.1`, `/data:C:\MU\Data`, `/frames:60`), with
    the names in any case, like the launcher's letters. `/?` and `/help` print the help. CLI11 gives this with
    `allow_windows_style_options()` and `ignore_case()`; the `--name` form keeps working too, so the CTest lines can
    stay the same on both systems.
  - `connect /u<host> /p<port>` works exactly as today: `connect` is optional, any order and any case, the value
    attached to the letter, one without the other or a repeat is an error, and `/y` and `/z` are rejected (Q-C36,
    Q-C37). It is how the lab and the original's launchers start the game. The launcher form and `/host`/`/port`
    together are an error.
- **Everything in English** (the 2026-11-21 rule): the option names, the value names in the help (`HOST`, `PORT`,
  `PATH`, `N`), the help and the messages. Only the launcher's `connect`, `/u` and `/p` keep their letters, because
  they are the original's.
- **One file per system, chosen by CMake, with no `#if`** (like `MakeObfuscation` in AR1.1). `App/CommandLine.h` keeps
  one `ParseCommandLine` and one `CommandLine`. The shared options live in `App/CommandLine.cpp` (the CLI11 side) and
  `App/CommandLineValues.cpp` (MuRet's rules for their values, with no CLI11); `App/CommandLinePosix.cpp` and
  `App/CommandLineWindows.cpp` give each system's syntax (`SystemSyntax`), read what is left after the options and turn
  a path argument into a path, behind `App/CommandLineSystem.h`. `Client/CMakeLists.txt` adds one of the two with
  `if(WIN32)`.
- **The library** (CODING_RULES §10, checked with Context7 on 2026-11-21). CLI11 (`cli11` in vcpkg, header only) does
  exactly both styles: `--opt value` and `--opt=value`, `--`, `-h,--help` by default, `set_version_flag("--version",
  …)`, and on Windows `allow_windows_style_options()` (`/name value`, `/name:value`) with `ignore_case()`. It builds the
  usage from the option declarations (`app.help()`), so the usage cannot drift from what the parser accepts. Every
  option keeps the last value (`MultiOptionPolicy::TakeLast`) and CLI11 counts them, so a repeat is MuRet's own error,
  `--frames is repeated`, the same for options and flags (`Throw` would give CLI11's text, which changed between
  versions). An optional value (`expected(0, 1)`) is not used: with it CLI11 2.4 to 2.6 drops the `--` after `--frames
  60` and reads the options after it. It cannot read the launcher form: a `/` short option takes no attached value, as
  the CL3 plan already found. So both systems parse with `allow_extras()`, and the per-system file reads `remaining()`:
  on Linux a leftover that starts with `-` is an unknown option and the rest is dropped; on Windows the launcher reader
  of today takes `connect`, `/u…` and `/p…`, and anything else is an error with the same usage. `/?` is looked for
  before CLI11 parses, so it wins over any error, as `--help` does over the values. CLI11 reads an empty attached
  value (`--config=`, `/data:`) as none and gives the option the next argument, so `ParseCommandLine` rejects it
  first (`--config needs a value`), and a flag with any attached value (`--stats takes no value`). The values are
  checked before the leftovers, because a missing value moves the next argument into them. CLI11 also unwraps a value
  written `[[…]]` (its escape for vector values); no MuRet value takes that form, so it stays. CLI11 throws
  `CLI::ParseError` (`CallForHelp` and `CallForVersion` for help and version). It is caught only inside
  `ParseCommandLine` and becomes a `Core::Expected`, with help and version as a result of their own that `main.cpp`
  prints to stdout before returning 0. No exception leaves `App/`.
- **The alternatives looked at** (Context7 and the vcpkg ports, 2026-11-21). Is a library needed at all? The hand
  parser of today would have to grow `--opt=value`, `--`, `/name:value`, names in any case and a usage generated from
  the options on two systems; that is what these libraries are for, so §10 says use one if it fits exactly.
  - CLI11 (`cli11`, header only, in Context7): fits both systems, as above. Chosen.
  - Boost.Program_options (`boost-program-options`, compiled, in Context7): GNU style yes (`unix_style`,
    `allow_unregistered` with `collect_unrecognized`, the help from `options_description`), but `/` only for one-letter
    options (`allow_slash_for_short`), so no `/data:C:\MU\Data`; `unix_style` guesses abbreviations unless turned
    off; it brings Boost into a repo that has none; and its README says the library is "essentially done": good PRs
    are merged slowly and issues may stay open indefinitely (53 open on 2026-11-21). Boost itself keeps releasing.
  - cxxopts (`cxxopts`, header only) and argparse (`argparse`, header only): only `-` and `--` options, no Windows
    style; Context7 has neither, so not verified beyond the CL3 plan.
  - docopt (`docopt`): parses from the usage text; not in Context7 and with no Windows style.
  - `getopt_long`: POSIX only, global state (`optind`), not in MSVC.
  - If CLI11 turns out not to fit when the milestone opens (warnings in the MSVC Debug build, a message that cannot be
    ours), the fallback is a hand-written parser with the same contract, and the PR says why. CLI11 needs no ADR: it is
    header only and only `App/CommandLine*.cpp` includes it.
- **Validation stays ours.** CLI11 collects strings, and after the parse `ParseHost` and `ParsePort`
  (`App/ServerAddress.h`), `ParsePositive`, `ParseMaxFps`, the values of `--pacing` and `--vsync`, and
  `PathFromArgument` (UTF-8 on Windows) check them, so the limits of Q-C37 stay the same.
- **What does not change:** `Resolve` (`App/Config.h`) and how the command line overrides the config; `--auto-login` and
  its environment variables; the raw line that `MainCheckFileName` (0x4ad270) reads, which `main.cpp` builds from
  `argv` and not from the parser. Nothing of the original's behavior changes either, because the original does not
  read arguments (Q-C36).
- **Tests.** `test_command_line.cpp` is split in three: the shared options (`--opt=value`, `--`, help, version,
  repeats) on both systems; `test_command_line_posix.cpp` (`--host`/`--port`; `connect /u10.0.0.1 /p44405` ignored,
  with no server and no error; an unknown `--option` gives its line and the usage, with exit code 2;
  `--data /usr/share/mu` is a path); and `test_command_line_windows.cpp` (today's launcher cases of Q-C36 and Q-C37,
  `/name value`, `/name:value`, names in any case, `/?`, the launcher form with `/host`). The tests' CMake adds each
  one only on its system. The `Client.Main.*` CTest lines switch to `--host 127.0.0.1 --port …` so they read the
  same on both CI machines, one Windows-only line keeps `connect /u127.0.0.1 /p0`, and the expected messages change
  to English.
- **Docs:** `Client/README.md` (the arguments table and the two examples, lines 175, 195 and 289 today) per system;
  D-C10 in the roadmap spec and the MuRet column of Q-C36 say the launcher form is Windows only and Linux uses
  `--host`/`--port` and ignores it; the header of `CommandLine.h` lists the options once, in English.
- **Considered and left out:** the XDG folders on Linux (`$XDG_CONFIG_HOME/muret` for the config, `$XDG_STATE_HOME`
  for the log) instead of the executable's folder. They are a Unix convention too, but they change where the config
  and the log live, not the command line; a later PR if Emanuel wants them. Short options other than `-h`: none until
  one has a use.
- **Order:** it depends on nothing in AR1.1 or AR1.2 and only touches `App/CommandLine*`, its tests, the CMake test
  lines and the docs, so it can go any time after AR0.1, next to any milestone that does not move `App/`. It has to land
  before AR5 moves `main.cpp` and `App/` to `app/`.
- **Verification:** the behavior golden identical (arguments do not reach the frame); the new tests and the
  `Client.Main.*` lines green on both CI machines; `check_layers.py` with no new row (`<CLI/CLI.hpp>` is a system
  include, which the check does not read).

**AR1 is done when** the engine builds without seeing `game/` and `app/`, and `check_layers.py` has no violation from
the `engine` root. AR1.3 does not hold AR2 back: it only has to land before AR5.

## Epic AR2: protocol and dispatch

### AR2.1 (design): packet layouts

- `engine/Network/Field.h` (`Client::Network`): `Field<T, Offset, Endian>` and a `PacketLayout` with type (C1 to C4),
  opcode, subcode, minimum length and the address of the original reader; a reader that accumulates the first error
  (without the 83 `if (!fields.HasValue())` and the 172 hand-written `TooShort`). `Core::ByteReader` stays for
  variable-length lists.
- **Where the reading lives** (Emanuel, 2026-11-23): in the engine, like XorRemap. `Field`, `PacketLayout`, the reader,
  `ReadList` and today's `ProtocolError.h` and `PacketFields.{h,cpp}` know only the C1 to C4 framing, the opcode and
  the subcode, which `Network/Packet.h` already holds. What is MU's stays in the game: each concrete layout and its
  writer in `game/Protocol/<Module>/`, and the opcode tables in `game/Session`.
- The four ways of reading become one: the 11 copies of `FieldsOf` and the two private `Fields` classes in
  `Protocol/Events.cpp` and `Protocol/CastleSiege.cpp` are deleted; the three list reads in `CastleSiege.cpp` become a
  `ReadList<Record, Size>`.
- `Protocol/` is organized by module (`Protocol/Guild/`, `Protocol/Items/`…), like `WorldPackets::<Feature>` in
  TrinityCore.
- **No code generator** for now (OpenMU generates from XML): the C++ descriptors already keep the offsets in one place.
  When AR2 closes we review whether the remaining repetition justifies one (CODING_RULES §10).

### AR2.2 (design): the opcode table and routing

- `game/Session/GameServerOpcodes.cpp` and `ConnectServerOpcodes.cpp`: `constexpr` tables with one row per `case` of the
  original dispatcher (`0x4e2b10` and its sub-dispatchers): type, opcode, subcode, address, handler, whether the original
  copies the packet into the ring before the handler and whether it expects encryption. `static_assert` with no repeated
  rows.
- `Unported{va}` for every `case` without a handler; a test compares the table with the research's list of `case`s
  (04-protocolo and the `0x4e2b10` switch), so a missing packet is a visible row.
- `Route<&Fn>` deduces from the handler's signature the layout and the parts of the `GameContext` to pass.
- `ServerSession` (2,878 lines) is split: `Session/Connection` (keepalive, serial, keys, the login and server change
  flow) and routing through the table. The first modules to switch to one handler per packet are login, selection,
  movement and the viewport.
- The `muret-packet` skill ("Skills for each step"), with a login packet as the example, and its line in `AGENTS.md`.

### AR2.3 (design): every handler in its module

- The rest of the 125 registrations become 40 to 80-line handlers in `game/<Module>/In/` (in `Scenes/` if the module
  has not moved yet, in its target folder from the map), and the session's ~50 send functions become actions in `Out/`.
- `App/WorldEvent.h`, `App/CharacterEvent.h`, `ISessionEventSink`, `SessionEventApplier` and `/bigobj` on `ClientLib`
  are deleted.
- **Verification of both:** the behavior golden identical; `tests/app/test_server_session.cpp` (5,575 lines) is split
  into per-handler tests with the same input bytes and the same assertions.

**AR2 is done when** adding a new packet touches its layout, its handler and one table row, and nothing else.

```text
AR0.1 ─► AR0.2 ─┬─► AR1.1 ─► AR1.2 ─► AR2.1 ─► AR2.2 ─► AR2.3 ─┐

```

- AR0.3 runs in parallel with AR0.1 and AR0.2. AR3.1 can start with AR2.1.
- AR1.3 (the command line) goes any time after AR0.1 and before AR5, next to a milestone that does not move `App/`.
- Within AR4, one milestone's design can run while the next one's move is generated.
- The port uses the third agent all the time; if the port becomes urgent, the refactor stops at a milestone boundary
  (every milestone leaves `main` in a complete state).
- The docs translation ([its plan](2026-11-21-docs-to-english.md)) goes before AR0.1 where it renames what this plan
  touches (AGENTS.md, CODING_RULES, the reference README), so the AR0 tasks edit English docs.
