# A thin main: findings and plan for the client's entry point

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `main.cpp` only builds the devices, in the order of `WinMain`, and starts the loop; what the original's frame
does lives in the game with a test, and the running client is composed in one place that both `main` and the behavior
golden build.

**Architecture:** today `main.cpp` holds three things in one file: the phases of the startup, the composition of the
running game (`RunScenes`) and pieces of the original's frame written as lambdas. Since `main.cpp` is not in the
library, the behavior golden copies `RunScenes` by hand. The plan separates them by one question each: what needs SDL,
GL or Winsock stays with the executable; what the original's frame does goes down to `game/Scenes` as functions; what
chooses the pieces and their order becomes `App::GameClient`, in the library, taking the devices as ports.

**Tech Stack:** C++20, GoogleTest, the behavior golden (`Client/tests/characterization`), `check_layers.py`.

**Spec:** the evidence in this document (there is no separate spec), the refactor design
[`2026-11-20-client-architecture-design.md`](../specs/2026-11-20-client-architecture-design.md), "Scenes as frame
scripts", and the master plan
[`2026-11-20-client-architecture-refactor.md`](2026-11-20-client-architecture-refactor.md), "AR1.4" and "Epic AR5".

Measured on `refactor/client` at fd1304c (2026-11-24). The other projects were read from their default branches the
same day. Signatures below use the names of that commit; by the time AR1.4 starts, AR1 has renamed some (`CrtRandom`
to `Crt`, `PixelSize` to `Core`, the engine namespaces after their folders), and the tasks use the name the tree has.

## The answer in short

- **`main()` is not the problem.** It is 87 lines, flat, in startup order, and it closes by declaration order. The
  `main()` of TrinityCore and of AzerothCore is almost four times longer, and MaNGOS Zero's almost three.
- **`RunScenes` is.** Its 283 lines and 10 lambdas hold parts of the original's frame: the tail of `WinMain`'s loop
  with the map music and Crywolf's, the keepalive speeds, the message clocks, the screenshot hooks. What those servers
  get right is that their main has no game logic: the loop calls one function of the game library.
- **The safety net tests a copy.** `main.cpp` is the executable's only source, so no test links it. The behavior golden
  rebuilds the composition by hand (`ScriptedClient`, about 350 lines, "the client as `RunScenes` in `main.cpp` composes
  it"), and CI runs `Main` only without a data folder, which never enters `RunScenes`. A change of order in `main.cpp`
  keeps every check green.
- **Recommendation:** one composition in the library, `App::GameClient`, built by `main` with the real devices and by
  the golden with its doubles, before AR2 starts changing that composition; the split of `main.cpp` by phases stays in
  AR5.

## What `main.exe` does

`WinMain` (`0x4b9b80`) is one long function, in this order
([02](../../../Client/docs/research/02-arranque-y-ciclo-de-vida.md#de-entry-al-bucle-de-mensajes)): the crash handler
(`0x67f4f0(0x4b9a70)`, the first call, at `0x4b9b97`), the texts (`0x61ee30`: `Text.bmd` and `Macro.txt`), the
launcher's update and server, the options (`0x4b90a0`), the video mode, the window (`0x4b8ff0`), the GL context
(`0x4b8e10`), the fonts, the volume, the timers, and the message loop, which runs the frame (`0x63945d`, then
`0x637700`) and, between frames, its own counters and timers. On `WM_QUIT` it runs three cleanups and returns.

What matters for the port is the order: the crash handler before anything, the texts before the window,
`srand(time)` (`0x4bad9a`) and the angle table (`0x4bada2`) before the first frame, the actor pool zeroed
(`0x4bafa6`), the first turn of the loop before the first frame, and inside each turn the order of the `rand()` calls.

- **Adopted, and MuRet already has it:** a flat main in startup order whose handles unwind in reverse (TrinityCore keeps
  one `make_unique_ptr_with_deleter` per started piece), and a named function for each step of more than a line
  (`StartDB`, `StopDB`, `GetConsoleArguments`).
- **Adopted, and missing:** no game logic in the entry point. Their loop is a few lines around one call into the game
  library, so the order of the tick has one home and a test can reach it.
- **Not copied:** the singletons that keep those mains flat (`sWorld`, `sConfigMgr`, `sLog`), which the spec already
  rejects in favor of injection; the `#ifdef _WIN32` blocks inside `main` (service, timer resolution), which here belong
  to `Platform`; a second entry class that only moves the length (cMaNGOS's own comment above `sMaster.Run()`: "Why do
  we need this 'Master'? Can't all of this be in the Main as for Realmd?"); MuMain's 2,680-line file, the shape this
  plan moves away from.

## The target

Three owners, one question each:

| Question | Owner | Tested by |
| --- | --- | --- |
| Does it need SDL, GL or Winsock? | the executable: `main.cpp` and, from AR5, the files next to it | CI's run of `Main` with a data folder (Task 4) |
| Is it something the original's frame does? | `game/Scenes` and below, as functions | unit tests and the golden |
| Does it choose which pieces exist and the order they are built and destroyed in? | `App::GameClient` (`app/App`, in the library) | the golden, which builds it with doubles |

`GameClient` lives in `App/`, not in `Scenes/`: the spec makes `app/` the composition root, it owns `App::AutoLogin`
(layer 12), and a new file in `Scenes/` that included it would add an upward include. `tests/app/` already links
`App/`. It is the master plan's `app/App/Composition.cpp` under the name of what it is.

### Where it fits in the AR plan

The master plan had one line for this, at the end: AR5 moves `main.cpp` to `app/App/Composition.cpp`. AR2 deletes the
event applier and turns `ServerSession` into a connection, AR3 introduces `GameContext`, and every AR4 milestone moves
state out of `WorldRuntime`: all of them edit the composition, and until AR5 each edit has to be made in `main.cpp` and
again in the golden's copy, with nothing checking that the two agree. So the composition moves first, as **AR1.4**,
after AR1.2 and before AR2.1, and AR5 keeps what is cosmetic by comparison: the phases of `main.cpp` in their own files
and `SceneManager` without its seven `std::function`.

## Global Constraints

- Fidelity first. These tasks change no order: the crash handler first, the texts before the window, the CRT seed, the
  angle table and the zeroed pool before the first frame, the first loop turn before `Start`, and inside a turn the
  order of the calls and of `rand()` as today.
- Every task is a refactor: no golden and no test expectation changes. If a digest moves, the task is wrong; the golden
  is never rewritten to make it pass.
- Devices are declared before the `GameClient` and outlive it, so shutdown stays the reverse of the declarations: the
  scene leaves and releases its textures while the texture table lives, the session closes while its socket lives.
- The message box of a fatal data error is shown while the client and the window are alive (Q-C180).
- Every address cited in a block that moves is cited where the block lands; the PR description gives the count of
  `0x` citations in the files it touches, before and after.
- Code that lands in a new file is cleaned there: named values per CODING_RULES §7, comments only if strictly necessary
  and in English, its own test. Texts the program logs do not change in these tasks.
- No file is renamed outside `move.py`. New files add their row to `Client/docs/research/coverage/module-map.tsv` in the
  same PR, and `check_layers.py` prints `0 new`.
- PRs target `refactor/client`, titled `refactor(AR1.4): …`. One task per PR, and Emanuel says yes before the next.
- GitHub CI is the build and the final word: the cloud container builds the client without SDL and GL, so it cannot
  build `main.cpp`.

## Review Focus

- A data folder and no host: there is no session, the poll succeeds without a network and `Exit()` never reports a
  server order. Task 3 pins it (`GameClientTest.RunsWithoutAServer`).
- A loop turn shorter than one original frame, or as long as several: the tail runs zero times, or once per original
  frame, and Enter is switched off either way. Task 2 pins both, and the faithful pace.
- Two reasons to stop in the same frame: the data error wins, then the scene's failure, the selection's, the server's
  order and the player's quit, as `main.cpp` checks them today. Task 3 pins the table (`GameExitOf`).
- The first keepalive after the world entry carries the own character's speeds. It leaves about 20 seconds after the
  GameServer connection and the longest scene of the golden lasts 9, so forgetting the call when the poll moves would
  pass. Task 3 adds the scene before it moves anything.
- Print Screen through the composition: the screen reader is asked once, on a frame the scene presents, and the file
  goes to the folder given. Task 3 pins it; the golden's copy never wired the screenshots.
